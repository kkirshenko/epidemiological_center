## 1. Запахи кода

### 1.1. Основные запахи, актуальные для проекта

| Запах | Где встречается | Признаки | Последствия |
|-------|----------------|----------|-------------|
| **Long Method** (Длинный метод) | `InspectionService.createInspection()`, `OrganizationController.searchOrganizations()` | Методы > 30 строк, множественные вложенные условия, смешанная ответственность | Сложность тестирования, низкая читаемость, риск регрессий |
| **Feature Envy** (Зависть к данным) | Контроллеры, обращающиеся к полям сущностей напрямую | `inspection.getOrganization().getRiskCategory()` вместо вынесения логики в сущность | Нарушение инкапсуляции, хрупкость кода при изменении модели |
| **Primitive Obsession** (Примитивная одержимость) | Использование `String` для статусов, `LocalDate` для дедлайнов без валидации | Магические строки `"PLANNED"`, `"HIGH"`, повторяющиеся проверки форматов | Ошибки времени выполнения, сложность рефакторинга |
| **Data Clumps** (Сгустки данных) | Группы параметров в методах сервисов | `(String name, String city, String riskCategory)` вместо `OrganizationSearchCriteria` | Дублирование сигнатур, сложность расширения поиска |
| **Duplicate Code** (Дублирование) | Валидация дат, нормализация статусов в разных сервисах | Одинаковые блоки `if (date == null) date = LocalDate.now()` в нескольких местах | Риск рассинхронизации при исправлении багов |
| **Long Parameter List** (Длинный список параметров) | Методы контроллеров с >5 параметрами | `createInspection(UUID orgId, String type, LocalDate date, String notes, UUID inspectorId)` | Сложность вызова, нарушение принципа единственной ответственности |
| **Anemic Domain Model** (Анемичная модель) | Сущности только с геттерами/сеттерами | `Inspection` без методов `isOverdue()`, `addViolation()`, бизнес-логика вынесена в сервисы | Потеря преимуществ ООП, сервисы становятся "божественными объектами" |
| **Magic Strings/Numbers** (Магические значения) | Хардкод статусов, кодов нарушений, сроков | `"CRITICAL"`, `90` (дней), `"FOOD_SERVICE"` вместо констант/энумов | Ошибки при опечатках, сложность поиска использований |
| **N+1 Query Problem** (Проблема N+1) | Загрузка проверок с нарушениями в цикле | `for (Inspection i : inspections) { i.getViolations(); }` без `JOIN FETCH` | Деградация производительности при росте данных |
| **God Class** (Божественный класс) | `OrganizationService` с 20+ методами | Класс, знающий слишком много: поиск, валидация, расчёт рисков, экспорт | Высокая связность, сложность тестирования, риск конфликтов при изменениях |

---

#### Приоритеты рефакторинга

| Приоритет | Запах | Ожидаемый эффект | Сложность |
|-----------|-------|------------------|-----------|
| **Высокий** | N+1 Query Problem | Ускорение загрузки списков в 5-10 раз | Низкая (`@EntityGraph`, `JOIN FETCH`) |
| **Высокий** | Magic Strings | Устранение ошибок валидации, типобезопасность | Низкая (замена на `enum`) |
| **Средний** | Long Method | Улучшение тестируемости, читаемости | Средняя (выделение приватных методов) |
| **Средний** | Data Clumps | Упрощение расширения поиска, чистота сигнатур | Средняя (введение `record`/DTO) |
| **Низкий** | Anemic Domain Model | Более выразительная доменная модель | Высокая (перенос логики в сущности) |

## 2. Подход к рефакторингу

### 2.1 Принципы рефакторинга в проекте

| Принцип | Описание | Применение в проекте |
|---------|----------|---------------------|
| **Red-Green-Refactor** | Сначала пишется тест, затем код, затем улучшение | Все изменения в сервисах предваряются unit-тестами на JUnit 5 + Mockito |
| **Small Steps** | Рефакторинг мелкими итерациями с постоянной проверкой | Изменения вносятся по одному запаху кода за раз, с запуском тестов после каждого шага |
| **Preserve Behavior** | Поведение системы не должно меняться | Все рефакторинги проверяются интеграционными тестами (`@SpringBootTest`) |
| **Measure Impact** | Оценка влияния на метрики качества | После рефакторинга перезапускается JaCoCo для контроля покрытия |

---

### 2.2 Процесс рефакторинга
Выявление запаха
↓
Локализация в коде (файл, метод, класс)
↓
Написание/обновление тестов для покрытия изменяемого кода
↓
Применение рефакторинга (инструменты IDE или вручную)
↓
Запуск тестов: unit → integration → полный прогон
↓
Проверка метрик: покрытие, сложность, производительность
↓
Фиксация изменений в Git с описанием в коммите

---

### 2.3 Инструменты поддержки

| Инструмент | Назначение | Конфигурация в проекте |
|------------|------------|----------------------|
| **IntelliJ IDEA Inspections** | Автоматическое обнаружение запахов | Включены проверки: Long Method, Duplicate Code, Magic Constants |

## 3. Data Mapper

### 3.1 Значение паттерна в проекте

**Data Mapper** инкапсулирует преобразование между доменными сущностями (Entity) и DTO (Data Transfer Object), обеспечивая:
- Изоляцию доменной модели от требований API и UI
- Гибкость в изменении формата данных без влияния на бизнес-логику
-  Возможность использования разных DTO для разных сценариев (create, update, view)

### 3.2 Преимущества подхода

| Преимущество | Реализация в проекте |
|-------------|---------------------|
| **Изоляция изменений** | Изменение формата ответа API требует правки только `toDto()`, не затрагивая сервис |
| **Разные DTO для разных сценариев** | `InspectionCreateDto` (минимум полей) ≠ `InspectionDto` (полный ответ) ≠ `InspectionUpdateDto` (опциональные поля) |
| **Тестируемость** | Маппер тестируется изолированно: `MapperTest` проверяет корректность преобразований |
| **Чистота сервисов** | Бизнес-логика не смешивается с кодом маппинга |

## 4. Identity Map

### 4.1 Значение паттерна в проекте
Паттерн обеспечивает, что каждый объект базы данных загружается в память только один раз в рамках одной транзакции. Это гарантирует, что все части приложения, ссылающиеся на одну и ту же запись БД (например, `Organization` с ID 5), работают с одним и тем же экземпляром объекта в памяти.

### 4.2. Реализация в проекте
В проекте паттерн не реализуется вручную, а делегируется **Hibernate Session (Persistence Context)**, который выступает встроенной реализацией Identity Map (также известной как First-Level Cache).

**Механизм работы:**
1.  **Ключ:** Уникальный идентификатор сущности (`id: UUID`).
2.  **Маппинг:** При первом запросе `repository.findById(uuid)` Hibernate загружает объект из БД и сохраняет его во внутренней карте `Session`.
3.  **Кеширование:** При повторном запросе того же UUID в рамках той же транзакции, Hibernate возвращает ссылку на уже загруженный объект, не выполняя SQL-запрос `SELECT`.

### 4.3 Преимущества использования

| Преимущество | Описание |
|-------------|----------|
| **Согласованность данных** | Изменение объекта в одном месте сервиса мгновенно отражается в другом, так как это один объект в памяти |
| **Производительность** | Сокращение количества SQL-запросов к базе данных внутри транзакции |
| **Отсутствие конфликтов** | Предотвращает ошибку `NonUniqueObjectException` при попытке сохранить дубликаты |
| **Прозрачность** | Разработчик работает с объектами, не задумываясь о ручном управлении кешем внутри транзакции |

## 5. Связь паттернов с качеством кода

Применение архитектурных и поведенческих паттернов напрямую влияет на ключевые атрибуты качества программного обеспечения.
Ниже приведена матрица соответствия паттернов, используемых в проекте, и обеспечиваемых ими характеристик качества.

### Матрица влияния

| Паттерн | Атрибут качества | Механизм влияния | Практический эффект в проекте |
|---------|------------------|------------------|-----------------------------|
| **PCMEF** | Поддерживаемость | Строгое разделение слоёв, инверсия зависимостей | Изменение UI или БД не требует переписывания бизнес-логики |
| **Repository** | Тестируемость | Абстракция доступа к данным, изоляция ORM | Лёгкое мокирование в unit-тестах сервисов (Mockito) |
| **Template Method** | Надёжность / Согласованность | Унификация алгоритмов CRUD, централизация валидации | Исключение дублирования кода, гарантия выполнения обязательных шагов |
| **Strategy** | Расширяемость (OCP) | Динамическая подмена алгоритмов без изменения контекста | Быстрое добавление новых критериев сортировки/фильтрации |
| **Builder** | Читаемость / Безопасность | Пошаговая инициализация, иммутабельность результата | Устранение «telescoping constructors», явная привязка параметров |
| **Observer (JPA)** | Целостность данных | Автоматическая реакция на события жизненного цикла | Гарантия актуальности `created_at`/`updated_at` без ручного контроля |
| **Data Mapper** | Изоляция изменений | Разделение доменной модели и DTO/API контрактов | Независимая эволюция внутренней структуры и внешнего интерфейса |
| **Identity Map** | Производительность / Консистентность | Кеширование объектов в пределах транзакции | Сокращение SQL-запросов, предотвращение дубликатов в памяти |

### Сводное влияние на метрики качества

| Метрика | До внедрения паттернов | После внедрения | Инструменты проверки |
|---------|------------------------|-----------------|----------------------|
| **Цикломатическая сложность** | Высокая (дублирование, вложенные `if`) | Низкая/Средняя (выделение методов, стратегии) | SonarQube / IntelliJ Inspections |
| **Покрытие тестами** | Низкое (тесная связь слоёв) | ≥ 41% (изоляционное тестирование слоёв) | JaCoCo 0.8.12 |
| **Связность (Coupling)** | Высокая (прямые вызовы БД из контроллеров) | Низкая (зависимость от интерфейсов) | Анализ зависимостей (jdeps) |
| **Скорость разработки** | Медленная (поиск багов в монолите) | Быстрая (параллельная работа над слоями) | Git history / Velocity |

### Соответствие принципам SOLID

- **S (Single Responsibility)**: Контроллеры обрабатывают HTTP, сервисы — бизнес-правила, репозитории — данные. Паттерны Repository и Data Mapper усиливают это разделение.
- **O (Open/Closed)**: Strategy и Template Method позволяют расширять поведение (новые алгоритмы, валидаторы) без модификации существующего кода.
- **L (Liskov Substitution)**: Все реализации репозиториев и сервисов наследуют базовые интерфейсы и могут быть заменены моками или альтернативными реализациями.
- **I (Interface Segregation)**: Специализированные интерфейсы (`InspectionRepository`, `ViolationService`) вместо «божественных» универсальных классов.
- **D (Dependency Inversion)**: Верхние слои зависят от абстракций (`IService`, `IRepository`), а не от конкретных реализаций Hibernate или JDBC.
