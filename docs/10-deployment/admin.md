# Администрирование

## Роль администрирования в проекте

В системе санитарно-эпидемиологического центра роль администратора (`ROLE_ADMIN`) является привилегированной и предоставляет расширенные возможности управления пользователями и мониторинга системы.

### Основные функции администратора

| Функция | Описание | Доступные эндпоинты |
|---------|----------|---------------------|
| **Управление пользователями** | Создание, редактирование, блокировка и удаление учётных записей сотрудников | `GET/POST/PUT/DELETE /api/admin/users` |
| **Изменение статуса пользователя** | Активация или деактивация аккаунта без удаления данных | `PATCH /api/admin/users/{id}/status` |
| **Просмотр метрик** | Доступ к сводной статистике и аналитике системы | `GET /api/admin/metrics` |
| **Назначение ролей** | Присвоение пользователям ролей `ROLE_USER` или `ROLE_ADMIN` | Через `POST/PUT /api/admin/users` |

### Технические особенности реализации

- **Ролевая модель** реализована через перечисление `Role` в модели `Profile`:
  ```java
  public enum Role {
      ROLE_USER,
      ROLE_ADMIN
  }
```

## Назначение администратора

Назначение роли администратора пользователю может быть выполнено двумя способами: при первоначальной регистрации или через панель управления.

### Способ 1: При создании пользователя (через API)

Достаточно отправить `POST`-запрос на эндпоинт `/api/admin/users` с указанием роли.

###Способ 2: Обновление существующего пользователя

Для повышения прав доступа существующего пользователя используйте PUT-запрос.

## Административные API endpoints

Данный раздел описывает REST-эндпоинты, доступные исключительно пользователям с ролью `ROLE_ADMIN`. Все запросы к путям `/api/admin/**` защищены Spring Security и требуют валидного JWT-токена в заголовке `Authorization`.

### Сводная таблица эндпоинтов

| Метод | Путь | Описание | Требуемые права |
|-------|------|----------|-----------------|
| `GET` | `/api/admin/users` | Получение списка всех пользователей (с пагинацией) | `ROLE_ADMIN` |
| `GET` | `/api/admin/users/{id}` | Получение данных конкретного пользователя | `ROLE_ADMIN` |
| `POST` | `/api/admin/users` | Создание нового пользователя | `ROLE_ADMIN` |
| `PUT` | `/api/admin/users/{id}` | Полное обновление профиля пользователя | `ROLE_ADMIN` |
| `PATCH` | `/api/admin/users/{id}/status` | Изменение статуса активности (`true`/`false`) | `ROLE_ADMIN` |
| `DELETE` | `/api/admin/users/{id}` | Удаление учётной записи | `ROLE_ADMIN` |
| `GET` | `/api/admin/metrics` | Получение сводной статистики и метрик системы | `ROLE_ADMIN` |

### Безопасность и доступ

- **Защита маршрутов**: В `SecurityConfig` настроено правило `.requestMatchers("/api/admin/**").hasRole("ADMIN")`
- **Аутентификация**: Строго через JWT. Заголовок: `Authorization: Bearer <token>`
- **Валидация**: Все входящие DTO проверяются через Jakarta Bean Validation (`@Valid`, `@NotBlank`, `@Email`, `@Size`)
- **Логирование**: Каждое административное действие фиксируется в журнале приложения с указанием `adminId`, типа операции и timestamp

---

### Создание пользователя

```http
POST /api/admin/users HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{
  "username": "inspector01",
  "email": "inspector01@sanepid.ru",
  "password": "StrongPass123!",
  "fullName": "Петров Пётр Петрович",
  "role": "ROLE_USER"
}
```

### Изменение статуса активности

```http
PATCH /api/admin/users/42/status HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{
  "active": false
}
```

## Панель администратора

Панель администратора представляет собой защищённый веб-интерфейс для управления пользователями, мониторинга системы и выполнения административных задач в санитарно-эпидемиологическом центре.

### Доступ к панели

#### URL доступа

http://localhost:8080/admin/dashboard

#### Требования для входа

| Параметр | Значение |
|----------|----------|
| **Роль** | `ROLE_ADMIN` |
| **Аутентификация** | JWT-токен или форма логина |
| **Сессия** | Stateless (токен сохраняется в localStorage) |

### Основные функции

#### 1. Управление пользователями

**Интерфейс включает:**

- **Список пользователей** с пагинацией и поиском
  - Отображение: username, email, роль, статус (активен/заблокирован)
  - Сортировка по дате регистрации, имени, роли
  - Фильтрация по статусу и роли

- **Создание пользователя**
  - Форма с валидацией полей
  - Выбор роли (ROLE_USER / ROLE_ADMIN)
  - Автоматическая генерация временного пароля (опционально)

- **Редактирование профиля**
  - Изменение контактных данных
  - Смена роли
  - Сброс пароля

- **Блокировка/активация**
  - Переключатель статуса без удаления аккаунта
  - Автоматическое завершение сессии при блокировке


#### 2. Журнал аудита

**Логирование действий:**

| Поле | Описание |
|------|----------|
| **Timestamp** | Дата и время операции |
| **Admin** | Кто выполнил действие (username) |
| **Action** | Тип операции (CREATE, UPDATE, DELETE, BLOCK) |
| **Entity** | Над каким объектом выполнено (User, Organization) |
| **Entity ID** | Идентификатор объекта |
| **Details** | Детали изменения (старое → новое значение) |
| **IP Address** | IP-адрес администратора |

**Пример записи:**
```json
{
  "timestamp": "2024-06-02T14:35:22Z",
  "admin": "admin1",
  "action": "ROLE_CHANGE",
  "entity": "User",
  "entityId": 42,
  "details": {
    "field": "role",
    "oldValue": "ROLE_USER",
    "newValue": "ROLE_ADMIN"
  },
  "ipAddress": "192.168.1.100"
}
```

## Эксплуатационные обязанности администратора

Администратор системы Центра гигены и эпидемиологии отвечает за стабильную, безопасную и эффективную работу приложения в производственной среде.

### Задачи

| Задача | Описание | Инструменты / Команды |
|--------|----------|----------------------|
| **Мониторинг доступности** | Проверка работоспособности API и веб-интерфейса | `curl -I http://localhost:8080/actuator/health`, Swagger UI |
| **Анализ логов** | Просмотр логов на наличие ошибок `ERROR`, `WARN` | `docker-compose logs -f --tail=100`, `grep "ERROR" logs/app.log` |
| **Проверка БД** | Контроль размера БД, наличия блокировок, долгих запросов | `pg_stat_activity`, `pg_stat_statements` |
| **Управление пользователями** | Создание, блокировка, сброс паролей сотрудникам | Панель администратора, `POST /api/admin/users` |
| **Резервное копирование** | Проверка успешности ночного бэкапа | `pg_dump`, скрипт `backup.sh`, мониторинг `/backups/` |

#### Типовые сценарии и действия

| Инцидент | Признаки | Действия администратора |
|----------|----------|------------------------|
| **Падение сервиса** | `502 Bad Gateway`, таймауты, `docker ps` не показывает контейнер | 1. Перезапуск: `docker-compose restart`<br>2. Анализ логов: `docker-compose logs app`<br>3. При необходимости — откат к предыдущему образу |
| **Перегрузка БД** | Медленные ответы, `too many connections`, high CPU | 1. Проверка активных запросов: `SELECT * FROM pg_stat_activity`<br>2. Завершение "зависших" сессий: `SELECT pg_terminate_backend(pid)`<br>3. Временное ограничение новых подключений |
| **Утечка токенов** | Множественные запросы с одного аккаунта с разных IP | 1. Принудительный выход пользователя: сброс `token_version` в БД<br>2. Блокировка аккаунта: `PATCH /api/admin/users/{id}/status`<br>3. Уведомление владельца аккаунта |
| **Ошибки валидации** | Рост `400 Bad Request` в логах | 1. Анализ паттерна ошибок (возможно, баг в клиенте)<br>2. При необходимости — временное ослабление валидации (через feature-flag) |
